# P19–P21：配置写入、应用与回滚

任务状态只记录在 [todo.md](todo.md)，本文件记录设计与依据。首个使用方是 Claude Code（P18 预览），
其后是 Pi、Grok Build 适配器、Skill 部署（P27）与 MCP 注入（P32）。

## 范围

本模块把已经预览过的计划落到磁盘，并且只在能证明安全时落盘：应用前重新核对计划令牌与目标身份、
同目录临时写入后原子替换、替换前留下私有备份、失败时给出明确状态。它不生成计划内容
（`config_plan.rs`）、不读取凭据（调用方在应用阶段从 OS 凭据存储取值）、不含界面：确认界面属 P20，
回滚视图属 P21，未完成操作的恢复入口属 P34。

安全规则：

- 不跟随目标路径最后一段的符号链接：链接目标可能已被替换，原子替换会写到别处。
- 不静默改变用户文件权限：已存在的目标沿用其权限位，新建目标默认 0600（可能承载凭据）。
- 只读目标拒绝替换，即使目录可写时 `rename` 仍能成功。
- 错误与日志只带稳定错误码和路径，不带文件内容或值。备份文件可能含用户已有密钥，因此只存放在
  私有目录（0700 / 0600），界面只拿到可定位路径与摘要。

## 单文件写入顺序

1. 读取目标，复用 `config_plan::read_target_bytes`：存在性、SHA-256、符号链接标记、1 MiB 上限。
   两边共用同一个读取器，避免「计划认为未变、写入认为已变」的分歧。写入器只比较精确字节，
   **不解析文档**：解析属于各自的适配器，否则第一个适配器的 JSON 假设会变成后来者的门槛
   （Grok Build 的设置是 TOML，按 JSON 解析会直接被当成不可读目标）。
2. 拒绝符号链接、只读目标与非普通文件。
3. 比对计划令牌：文件出现、消失或内容变化一律返回 `target_changed`，绝不覆盖。
4. 新内容与现状一致时返回 `changed: false`：不写盘、不备份、不改时间戳，连续提交因此安全。
5. 目标存在时先把当前字节写入私有备份（`<backups>/<id>/<文件名>`，目录 0700、文件 0600）；
   备份失败则不写目标。
6. 同目录创建临时文件（`.<文件名>.vibemate-<id>.tmp`，权限沿用目标或 0600），写入后 `sync_all`，
   再 `rename` 覆盖目标；成功后同步父目录（Unix）。
7. 重新读取目标并回报新摘要；重读失败或摘要不符返回 `outcome_unknown`，不报成功。

`rename` 在同一文件系统内原子，所以目标文件只会是旧内容或新内容，不会出现半截文件。Windows 上
`rename` 同样替换已存在的文件，但目标被其他进程独占打开时会失败；平台差异在 P37 记录。

## 多文件操作（P19.b）

一个计划可能覆盖多个目标（Pi 的设置与模型定义、技能部署路径、MCP 配置）。多文件按步骤应用：
每步记录目标、期望摘要、结果与备份引用；任一步失败后回滚已应用的步骤，无法回滚时保留明确的
未完成状态，绝不报告整体成功。操作与步骤写入 SQLite，重启后能列出未完成操作供 P34 处理；
补偿只操作 vibemate 自己写过的目标。

### P19.b1：操作日志（2026-10-14 交付）

SQLite schema v16 新增 `config_operation` 与 `config_operation_step`，仓储在
`config_apply/operations.rs`，测试在 `config_apply/operation_tests.rs`：

- 每次操作在替换任何文件之前写入：操作行为 `planned`，每个目标一行 `pending` 步骤，含路径、
  期望摘要与时间戳。步骤按序号排列，序号必须连续。
- 步骤结果分开记录：应用成功写入新摘要与备份引用，失败写入稳定错误码；两个写入都在事务里
  同时刷新操作的 `updated_at`。
- 未完成 = 不是已知的已结束状态（`applied`/`failed`/`compensated`）。这样本版本不认识的取值会
  以 `invalid_stored_operation` 报出，而不是从列表里静默消失。
- 数据库只保存路径、摘要与错误码：有测试写入真实备份后扫描数据库文件，确认密钥不出现在其中。
- 读取重新校验每一行（身份形状、digest 格式、错误码形状、序号连续、状态与字段搭配、路径可显示），
  畸形行报错而不当作真实结果。

本批不含编排与补偿（P19.b2）与界面（P34）。

### P19.b2：多文件编排与补偿（2026-10-14 交付）

`config_apply/service.rs` 与 `config_apply/service_tests.rs`：

- `apply_files(storage, kind, files, backups)`：先用 `begin_operation` 记录整个计划，再按顺序对每个
  文件 `apply_file` 并记录该步骤的结果；全部成功记为 `applied`。
- 任一步失败时记录失败步骤与稳定错误码，然后调用 `compensate_operation` 回滚，并返回最终状态而不是
  错误：`failed` 表示没有任何文件被替换，`compensated` 表示全部回滚，`partial`／`unknown` 表示有文件
  无法回滚（例如用户后来改过它），此时操作留在未完成列表里供 P34 处理。只有操作日志本身不可信时才
  返回错误，因为那时无法诚实报告结果。
- `compensate_operation` 也可用于更早留下的未完成操作（P34 的恢复入口）：它按记录的步骤倒序处理，
  从不触碰未应用的步骤。
- `restore_file` 读取备份并校验其摘要，再通过 `apply_file` 写回，因此回滚同样受令牌检查、私有备份与
  原子替换保护；`remove_created_file` 只删除内容仍等于本模块写入值的文件，文件已不存在按成功处理。
- 回滚会丢弃它自己产生的那份备份（操作记录已说明发生了什么）；创建文件的那次写入没有备份，回滚时
  直接删除。

已知边界：步骤状态只有 `pending`／`applied`／`failed`，回滚结果记在操作状态上，不逐步骤标记；界面若
需要逐步骤结果，用 `ALTER TABLE ADD COLUMN`（v17）补一列即可。日志目前只增不减，已结束操作的清理
策略仍未定。

首个把计划写到磁盘的功能。Rust 侧（`agents/claude_code.rs`，P20.a 已交付 2026-10-14）：

- `apply_claude_code_settings(storage, credentials, input)`：先用与预览完全相同的 `build()` 重新读取
  当前 Provider、模型与设置文件，再把界面回传的四个令牌（目标路径、文件摘要、Provider `revision`、

- 令牌通过后才读凭据：引用名由存储的 Provider ID 生成（`provider-<id>`），取值放入计划显示的占位符
  位置。密钥不进入计划、返回值、错误或日志；返回值只带状态、逐文件结果与备份路径。
- 写入复用 P19 的 `apply_files`（操作类型 `claude_code_settings`），备份根目录为应用数据目录下的
  `backups/`，因此替换前的设置内容可在该目录定位，操作也会记入日志。
- 结果 `ClaudeCodeApplied`：`state`（`applied` 或回滚后的状态）、逐文件 `steps`（含 `errorCode` 与
  `backupPath`）、`backupPath` 与 `restartRequired`。文件级失败是结果而不是错误：界面按 `errorCode`
  翻译并提示重新预览或处理冲突。
- 错误码：`plan_stale`、`credential_missing`、`credential_unavailable`，加上预览已有的
  `gateway_unverified`／`base_url_unverified`／`target_unreadable`／`target_conflict`／
  `provider_not_found`／`model_not_found`／`location_unavailable`／`storage_unavailable`／
  `invalid_request`／`operation_failed`。

### 每次实际改写前留下独立快照（H1）

- 应用模型配置、参数修改、手动恢复历史版本，以及自动补偿等实际修改目标的路径，均在替换或
  删除前保存完整原文件字节、存在状态和摘要；成功改写的快照不可被后续写入或恢复覆盖、自动清理。
  第一次快照就是首次注入前的原内容，不以重新序列化的配置代替原字节。
- 文件原先不存在时记录“不存在”，恢复该状态表示删除新建文件；无内容变化的提交标为无变更，
  不冒充新版本。备份或必要日志无法可靠保存时拒绝写入。多文件操作逐文件记录，并明确部分失败。
- 手动恢复应成为有来源关联的新历史操作，保留恢复前的快照，让用户可以撤销这次恢复。
  自动补偿关联原失败操作，必须保留其实际改写前的快照，但不得被启动恢复误认成需要反向重放的操作。
  实现前重新设计操作状态、恢复状态与 P34 未完成操作处理，不能只在旧回滚函数外增加日志。
- 历史按 Agent 和配置根隔离；界面可分页或加载更多，访问全部保留记录而不只是最近 10 条。
  每条显示时间、操作种类、来源版本、目标文件、结果、备份可用性和恢复/删除入口，兼容旧日志与缺失备份。
- 当前配置固定显示在列表第一条，不随历史分页移动；其余历史按时间倒序排列。当前标记由实际文件摘要
  核对，不能只根据最后一次操作推断。匹配已有快照时将该版本置顶并标记“当前配置”，不自动删除或
  消费它的历史快照；恢复 B 后 A、B、C、D 都保留，B 置顶，恢复操作另记。多个相同内容的历史记录
  保留各自身份，只用一个置顶条目表示当前状态。外部修改、未记录配置、读取失败和多文件部分匹配
  明确显示实际状态，不误标某个历史版本为当前完整配置。当前已匹配版本不提供无意义的重复恢复操作。
  用户主动删除当前版本的备份时，仅删除对应历史及备份，不删除当前配置文件；置顶的当前状态仍显示。

### H1 首批：独立的逐文件改写日志

先交付后端快照，不改变现有 IPC。追加 schema v20 的 `config_file_revision`，每条记录关联原
`config_operation_step`，并用独立的批次 ID 将一次手动恢复或自动补偿的多个文件关联起来。
意图区分 `apply`、`restore`、`compensation`；这些记录不是旧操作队列的待补偿操作，P34 不得
将其反向重放。原操作和旧 `restore_state` 暂时继续服务现有界面；H2 再开放直接恢复这些版本。

实际替换或删除前，先同步私有备份，再提交 `prepared` 日志（含原存在状态、摘要、备份引用和
目标摘要；删除的目标摘要为空），之后才触碰目标。成功并核对后记 `completed`，明确未成功记
`failed`，落盘结果无法确认记 `unknown`。结果日志写入失败保留 `prepared`，不能假称操作没有
发生；后续历史/P34 必须结合实际文件核对，不自动重放。不变更不生成版本，备份/前置日志失败
不改目标。恢复和补偿生成的快照独立保留，不再作为临时副本删除。

旧日志原样保留，不补造旧版本的恢复前快照；已有备份仍按旧规则恢复，无法证明的状态保持未知。
`prepared`／`unknown` 暂时阻止该原操作的继续恢复/补偿，避免错误重放；实际文件核对与解锁入口须在
H1 后续/P34 交付。前置日志失败时目标保持原样，但已刷盘的私有副本可能尚未被数据库引用；这些副本
不自动删除，后续清理设计须包含这类残留，不能把它们当成已完成版本。
本批验证多次写入、无文件状态、恢复/补偿、备份/日志故障和重启。全部历史浏览、当前版本核对、
任意版本恢复和删除仍分别属于 H1 后续、H2、H3，不随此后端批次提前标记完成。

### H1 后续批次：先只读核对，再显式解决

本轮先提供按原操作读取未完成改写的后端接口，不新增 IPC 或界面。核对 `prepared`／`unknown`
记录关联的真实步骤、目标摘要和私有备份；逐文件报告匹配改写前、匹配目标、两者均匹配、外部变化或
不可读取，并独立报告备份完整性。不存在与空文件保持不同。路径、摘要和错误码可返回，文件字节不可返回。
读取不更新日志、不改文件，也不解除旧恢复保护；核对只是某一时刻的观察，不能作为以后写入的授权。

验收使用临时目录和 SQLite 故障注入，覆盖应用/恢复/补偿方向、创建/删除、不确定结果、重启、外部变化、
损坏/丢失备份、符号链接、超限和畸形日志。运行 Rust fmt、Clippy、全量测试与锁定桌面构建。
显式解决批次在同一 SQLite 写事务中重新核对审批内容、更新快照与旧步骤，并记录解决依据（追加 schema
v21 的 `config_revision_resolution`，不改 v20）。仅接受明确匹配改写前或目标且快照可用的记录；
歧义、外部变化和不可读保持阻止。解决只记录当前观察，不声称能证明是谁写过文件或是否发生过瞬时改写；
不改配置、不读凭据、不自动补偿。审批绑定整个原操作的元数据摘要和完整候选集合，文件或记录变化即过期。

同时覆盖另一个中断窗口：快照已记 `completed`，但旧步骤结果没写入。核对与旧恢复保护必须识别这类记录，
不能仅依赖 `prepared`／`unknown`。只修复每步最后一次已记录改写；更早的未解决记录保守阻止，不猜测顺序。
应用匹配目标时补全旧步骤的备份、原存在状态与写入摘要；匹配改写前时记应用未达目标。
恢复/补偿匹配目标时标记该旧步骤已恢复，不能反向重放；匹配恢复前时标记恢复未达目标、保留重试能力。
解决依据与这些更新同时提交，任何日志失败全部回滚。操作结果按修复后的步骤汇总，未执行步骤不冒充成功。
应用、手动恢复、补偿和显式解决先取得 SQLite 同目录的永久 `.config-lock` 文件独占锁，再取得数据库锁；
用标准库 `File::lock`（macOS/Linux 为 flock，Windows 为 LockFileEx），句柄释放即解锁，锁文件不删除。
这防止另一个实例把仍在改写的 `prepared` 当作中断记录；不锁外部 Agent/编辑器，不替代摘要检查。
官方依据：[Rust File::lock](https://doc.rust-lang.org/std/fs/struct.File.html#method.lock)。

测试覆盖三种方向、创建/删除、多文件、重启、两处结果日志中断、过期确认、重复确认、跨操作确认、备份损坏、
歧义与事务故障；运行 Rust fmt/Clippy/全量测试和锁定桌面构建。本批不新增 IPC 或界面；
后续交付解决/恢复界面入口、未引用私有副本管理、历史分页与当前版本界面。

### H1 中断核对与显式解决入口

本批把已交付的后端核对/解决接到三种已支持 Agent 的历史行，不扩展为自动恢复。
历史行由 Rust 标明是否仍有中断记录；需要核对时不提供旧恢复按钮。用户主动核对后，按文件查看
改写方向、记录阶段、当前摘要匹配关系和备份可用性。后端依据同一解决校验规则决定是否可确认；
歧义、外部变化、不可读、备份不可用或被后续改写取代的记录保持阻止。

IPC 只接受固定的三个 Agent 身份、操作 ID 和完整核对计划的摘要，不接受任意配置/备份路径、
文件内容或前端重组的观察结果。后端先核对操作归属，再读取目标；确认时重新构建并比对整个计划，
最后复用带跨实例锁和事务的解决接口。旧步骤、所有候选和观察变化都使确认过期。
解决成功只表示已记录当前观察，不证明是谁写过配置，也不表示会话已生效。确认后丢弃核对计划、
重新读取历史，任何配置恢复仍需独立预览和确认；不自动调用补偿或恢复。

前端同时交付中英文、读取/失败/重试/取消、重复提交防护和页面卸载后的异步结果保护。
验证覆盖三 Agent 归属、严格请求和响应、过期/重复确认、阻止项、确认后历史刷新与独立恢复。
完整历史分页、配置根隔离和当前版本固定展示仍是 H1 后续，不在本批冒充已完成。

### H1 未引用私有副本管理

本批只增加后端检查与显式清理，不接 IPC/界面、不自动运行，也不删除历史记录。检查同时读取
`config_operation_step` 与 `config_file_revision` 的全部引用，不按操作状态或最近条数过滤；
被任一日志引用的目录均保留，日志不可读或引用路径畸形时拒绝清理。

检查与清理先取跨实例配置锁，再取 SQLite 写事务，避免把尚未提交前置日志的活动备份当成残留。
只接受写入器生成的数字三段目录名，以及空目录或单个有界普通文件；链接、嵌套目录、多个文件、
超限或不可读内容保留并报告阻止路径。只返回路径和摘要，不返回文件内容。

清理必须显式提交已检查的候选，执行前重新检查引用、目录布局和内容摘要；变化即要求重查。
每个目录只逐项删除已确认的普通文件和空目录，不递归删除。未引用目录本身就是重启后的待处理清单：
失败或中断后重新检查并重试，不先隐藏副本、不删日志；已消失候选的重复清理视为完成。
若只删掉文件但未删掉目录，重新检查会得到空目录候选。无需为这类没有历史引用的副本新增数据库迁移；
H3 的历史记录删除仍需独立的持久删除状态。文件删除不是安全擦除。

验证覆盖前置日志失败、重启、旧步骤单独引用、快照单独引用、恢复/补偿快照、过期候选、畸形引用、
未知目录布局、链接、超限文件、部分清理失败与重试，以及跨实例锁等待。运行 Rust fmt、Clippy、
全量测试与锁定桌面构建；不改真实 Agent 配置，Windows/Linux 原生验证仍留到发布前。

### H1 后续批次：配置根限定的只读历史分页

现有最近操作列表不能代表全部改写：手动恢复和自动补偿保存在独立的 revision 批次里。
`config_apply::configuration_history` 通过 `HistoryScope`、`HistoryCursor` 和 `HistoryPage`
提供只读查询，不接 IPC/界面、不改变现有恢复入口或配置文件，也不新增迁移或依赖。
`HistoryScope` 不是可反序列化的前端路径输入，必须由可信 Rust 调用方构造。

- 查询范围由可信 Rust 调用方传入 Agent 操作种类、配置根及已拥有的直接子文件名；只纳入全部
  步骤均属于该范围的操作。不用路径前缀匹配，不跟随链接或合并路径别名，配置根不必仍然存在。
- 原操作始终保留一个条目，携带其 apply revisions；每次 restore/compensation 批次另列，
  多文件同一批次不拆页。旧日志、尚未生成 revision 的失败/未完成操作仍可查询。
- 按条目创建时间及稳定身份倒序，用绑定范围的游标加载下一页，每页限制 1–50 条。
  多文件批次以最早插入行的时间排序，后续文件发生时钟回退不会改变批次位置。
  一页使用同一个 SQLite 只读事务快照；不同页面是实时视图，不承诺冻结整个历史会话。
  游标是上一页最后条目的排序位置，不是签名审批或授权；每次查询仍重新限定范围。
  不用 offset，新增较新记录不挤动后续页，刷新首页才能看到它们。
- 只返回已验证的身份、时间、状态、目标路径、摘要及“记录过备份引用”元数据；不读取配置或
  备份字节，不返回备份路径，不将备份引用误报为备份可用，也不推断当前版本或恢复资格。
  原操作步骤和本批次改写结果分别返回；显式解决审计保留解决前状态、观察摘要和匹配方向，
  不能将修复后的状态当作原进程确实执行过写入的证据。
- 验证三个 Agent、多配置根及相似前缀隔离、超过 10 条/同时间戳分页、重启、恢复/补偿分组、
  空页/边界、无 revision 记录、错误范围游标、观察审计及独立连接并发更新。选中条目的
  畸形元数据报错，不跳过后假装历史完整。范围最多 16 个文件，每个操作/批次最多 16 项，
  超限报错而非截断。任务状态只记在 `todo.md`。

完整界面、备份可用性检查和当前配置置顶仍属后续批次，不因这个查询完成而标记 H1 整体验收。

### H1 只读分页 Rust IPC

`configuration_history_page` 命令接受严格的 `agent`、`after` 和 `limit` 请求，调用
`agents::history` 域边界。仅允许 Claude Code、Pi 与 Grok Build；环境来自桌面进程，配置根
复用只读发现的优先级，不接受前端传根路径或 CLI 入口。无效覆盖不退回默认根；不用当前安装版本
作为历史访问门槛，Agent 已卸载或配置目录不存在时仍可读取记录。

受管文件固定为 Claude Code 的 `settings.json`、Pi 的 `models.json`/`settings.json`、
Grok Build 的 `config.toml`，不把凭据优先级文件或未拥有字段文件纳入历史范围。响应直接使用
已有安全 `HistoryPage`，没有文件内容、备份路径、备份可用性或恢复授权。复用当前存储状态与阻塞

不是这些操作的审批令牌。

前端 `readConfigurationHistory` 现已接入此命令，使用 Zod 严格 Schema 校验响应，拒绝未知字段、

IPC，也不伪造空的桌面历史。原操作结果、各批次逐文件结果与核对观察仍分别保留。

### H1 历史界面切换到配置根限定的分页 IPC

`RestoreView` 不再调用只取最近十条的旧列表命令，而是从 `readConfigurationHistory` 读取当前
Agent/配置根的第一页，并用「加载更多历史」以游标追加更早条目。多文件批次不拆页；追加失败
保留已读条目并重新提供按钮，不把读取失败说成历史结束。切换 Agent、重新检查、恢复成功或记录核对
观察都会重新读取第一页，旧的分页位置不再使用。

为保留已验收的操作入口，分页 IPC 的响应在共享日志字段之外补充两项只读元数据；两者都来自
SQLite/服务商记录，不读取配置或备份字节：

- `requiresResolution`：源操作是否仍有中断改写。为真时行内只提供既有的核对入口，不提供恢复
  预览；该判断与后端恢复保护使用同一个查询。
- `ownerLabel`：`ownerRef` 仍对应已保存服务商时的显示名。服务商已删除时保留原始引用并显示
  「已不在库中」，不猜测名称。

界面按条目显示操作种类（应用/手动恢复/自动补偿）、操作状态或批次中最不确定的单文件结果、
时间、目标文件与逐文件结果，以及服务商信息。批次的逐文件状态来自独立 revision；没有
`sourceState` 的批次不合成一个「整体成功」状态。应用条目始终提供只读恢复预览：分页查询按设计
不读取目标文件，因此「当前是否还有可恢复内容」由预览回答，预览会明确报告无操作；这不放宽
写入前的摘要校验。

本批仍不验证备份实际可用性、不识别或置顶当前版本、不提供历史删除，也不恢复任意批次快照
（H2/H3）。旧的最新十条 IPC 与前端封装暂时保留但界面不再调用，待新界面验收后随清理批次移除。

### 任意历史版本可预览并恢复（H2）

- 用户可直接选择任一保留记录，恢复到该次写入前的状态，包括最初原始状态；不要求先逐条撤销
  中间写入，已经恢复过的记录也仍可作为版本来源。恢复只针对该记录涉及的文件，不伪装成全机快照。
- 后续合法写入不应使旧版本永久变成“冲突不可恢复”。预览以当前文件为比较对象，展示当前到
  所选快照的脱敏差异，明确会撤销的后续配置和手动修改，用户再次确认后才执行。
  这不是无提示强制覆盖：预览后的任何并发变化都使计划过期，必须重新预览。
- Rust 校验快照摘要、目标归属、路径/符号链接和文件权限；备份损坏/丢失或旧记录无法证明原状态时
  阻止恢复并说明原因。凭据不返回前端、不进入日志；恢复可能写回旧明文密钥，界面必须提示，
  不改中央 OS 凭据。恢复本身遵守 H1，写入结果与运行中会话是否生效分开显示。

#### H2 后端首批：按历史条目恢复任意保留版本

本批只交付恢复规则，不新增 IPC 或界面；两层预览、文本脱敏与确认交互仍在后续批次。
`config_apply/version_restore.rs` 接收可信 Rust 调用方构造的 `HistoryScope` 和条目身份
（`operation:<id>` 或 `batch:<id>`），不接收前端路径：

- **条目级恢复**：应用条目恢复到该次应用前的状态；恢复/补偿批次恢复到该批次改写前的状态。
  多文件条目逐文件处理，恢复/补偿批次只涉及自己的文件子集。已恢复过的条目仍可作为版本来源。
- **版本来源**：应用条目优先使用该次写入保留的 apply revision；旧日志或未变更新增步骤没有
  revision 时，以步骤记录的 `expected_digest` 作为目标版本。当前文件已等于目标时标为无需处理；
  文件已变化却没有保留字节时以 `snapshot_unavailable` 阻止，不伪造旧内容。
- **快照校验**：`config_apply/snapshots.rs` 统一验证私有副本必须位于
  `<backup-root>/<revision-id>/<目标文件名>`，目录链不是链接、文件是普通文件、不超过目标上限且
  摘要等于记录的改写前摘要。检查与恢复写入共用这一实现，核对界面也改用它。
- **阻止而非猜测**：符号链接、不可读/超大目标、只读目标、缺失或损坏快照、跨 Agent/配置根/文件
  范围、未解决的中断记录（`history_unresolved`）均使整条计划不可恢复。多文件条目只要一个文件
  被阻止，确认也不会只恢复其余文件。
- **并发令牌**：预览返回当前文件摘要；确认时在跨实例配置锁内重建同一计划并逐文件比对，任何
  文件、快照或日志变化返回 `plan_stale`，不写字节。写入时再次校验快照摘要与目标令牌。
- **恢复可撤销**：实际写入走共享的 recorded-write 路径；替换前先保存当前完整字节，删除前也先
  保存。恢复因此记录为新的独立批次，用户可再恢复它替换掉的状态。快照永不因恢复而删除。
- **不污染旧回滚语义**：直接版本恢复在 schema v22 中以 `direct = 1` 标记，存储方向仍是
  `restore`；历史视图把它显示为 `version_restore`。它不更新源操作的 `restore_state`，已完成的
  直接恢复也不会被误判为“旧步骤结果缺失”。若直接恢复自身中断，仍按现有核对流程显式记录观察，
  但不修复源步骤的旧回滚结果。

本批验证 A→B→C 直接恢复 A、再恢复该恢复批次回到 C；无文件状态、快照缺失/损坏、符号链接、
只读目标、预览后并发修改、跨 Agent/根/文件范围、旧日志无快照、Provider 归属及中断恢复的核对。

#### H2 IPC 与前端严格边界

`plan_configuration_version_restore` 与 `apply_configuration_version_restore` 复用历史查询的
发现环境优先级，只接受 Agent、条目身份（`operation:<id>` / `batch:<id>`）以及 apply 时逐文件的
`revisionId`/`currentDigest`；不接受配置根、备份路径或文件内容。apply 在取得存储与配置锁前先
拒绝空列表、超过 16 项、畸形 revision 身份或摘要；领域层仍会重建计划并逐项比对。命令只返回
计划/结果元数据，不含备份路径或配置字节。

前端 `src/lib/desktop/versionRestore.ts` 用严格 Zod Schema 校验：

- `restorable` 必须等于“存在 restore/remove 且没有 blocked”；`blocked` 必须有理由，其他动作
  不得带理由；`restore`/`remove` 必须有 revision 身份与符合方向的目标摘要，`skip` 要求当前摘要
  已等于目标。
- 操作条目必须是 `intent = apply` 且 `operationId` 与条目身份一致；批次条目不得为 `apply`；
  文件序号与 revision 身份在一页内唯一。
- 结果中的每个文件必须来自本次 reviewed 集合，状态与错误码互相一致；整页畸形即拒绝，错误只保留
  稳定码，不保留响应或 Zod 诊断。
- 浏览器预览不调用 IPC，也不伪造计划；apply 在浏览器中返回 `desktop_required`。

#### H2 两层预览与确认界面

`config_apply/version_text.rs` 为每个文件生成两层内容：

- **字段摘要（默认层）**：比较当前与保留版本，逐字段列出 `added`/`removed`/`replaced`、
  路径和脱敏旧值/新值。不存在、空字符串与 `null` 分别显示。数组按索引、对象按文档顺序递归；
  容器整体增删展开到叶子。单文件最多 200 项，超出时 `truncated = true`，界面明确提示而不是
  静默截断。文档无法解析时摘要返回 `text_unavailable`，不返回原文。
- **完整文本（详情层）**：仅在用户点击“查看详细配置”时读取。JSON 重新格式化为缩进 JSON；
  TOML 用 `toml_edit` 保留注释、键顺序和排版。原始字节与脱敏后文本分别限制为 1 MiB；
  JSON 缩进扩张超限时返回不可用，不截断后冒充完整文本；
  每一侧独立返回 `absent`、`present { text, bytes }` 或 `unavailable { reason }`。
- **脱敏**：按配置中的所有键名匹配凭据类字段，而不是只处理 vibemate 写入的字段。覆盖
  `api_key`/`apiKey`/`x-api-key`、`Authorization`、`ANTHROPIC_AUTH_TOKEN`、`clientSecret`、
  `password`、`private_key`、`access_key` 等；`max_tokens`、`input_tokens`、`env_key`
  （引用而非凭据）与 `apiKeyHelper` 不误伤。命中键的整个值（包括嵌套对象/数组）替换为固定
  占位符。摘要和完整文本共用同一规则；无法解析或无法确认安全时只返回原因，不返回未脱敏文本。
- **绑定同一计划**：详情请求携带预览时的当前摘要；Rust 重新构建计划、重新读取快照并再次
  校验，文件或日志变化返回 `plan_stale`。详情与摘要不会混合两个不同时刻的文件。

界面 `VersionRestorePlanCard` 默认展示每个文件的动作、阻止原因、字段摘要与脱敏标记；
`VersionTextDialog` 提供文件切换、当前/保留两栏、只读语法高亮（无 HTML 注入）和带行号的
有界行级差异。差异超过比较上限时明确提示改为人工对比，不声称完整。对话框使用 Base UI
处理 Escape、标题初始焦点与关闭后焦点返回（不因聚焦底部关闭按钮而跳过长内容开头）；
读取失败可重试；缺失侧显示“不存在”，不可用侧显示
原因。确认只发送摘要中会改动的文件及其当前摘要，成功后重新读取历史并保留可撤销的新恢复批次。

历史行按以下顺序选择入口：仍有中断写入时只提供核对；条目有保留 revision 时使用 H2 版本恢复
（应用、恢复与补偿批次均适用）；仅旧日志、无 revision 的应用条目继续使用旧回滚入口。这样
旧日志的最小回滚路径不丢失，同时新条目不再受“文件被后续合法写入修改即永久冲突”的限制。

H2 已完成隔离 macOS Tauri 运行时验证和浏览器人工检查（2026-10-19，代理执行，不冒充维护者确认）；
三 Agent 使用合成 OS 凭据验证 A→B→C 后直接恢复 A、撤销恢复回到 C、最终逐字节还原，
Pi 同时验证不存在的文件被删除和重建。过期摘要/详情/恢复均被拒绝；重复恢复正确显示跳过，
已经匹配目标的文件保留目标摘要，两侧都不存在时不再产生无效根字段。外部将 JSON 改成标量时，
根级变化使用明确的 `$` 路径，不返回空路径。Windows/Linux 留在发布前专项。

#### 模型配置复用两层预览

Claude Code、Pi 与 Grok Build 的模型配置均通过只读 `read_model_configuration_preview`
取得相同格式的字段摘要，点击详情时才请求所选文件完整文本。Rust 复用各适配器实际写入的原生
构建器，重新检查所选安装合约、Provider/模型、别名与所有文件令牌，将完整计划与已审阅计划精确
比较；再次读取的文件字节也必须匹配计划摘要。前端提交的路径只参与计划比较，不用作读取目标；
不接受未知请求字段、不支持的 Agent、越界文件索引或超过 1 MiB 的审阅计划。不读取 OS 凭据。

`ModelPlanPresentation` 和恢复界面共享字段呈现与 `ConfigurationTextDialog`；模型预览两栏为
“当前配置 / 计划写入配置”，历史恢复则为“当前配置 / 保留版本”。摘要未成功读取前不允许应用；
详情读取失败可重试，计划过期仍须重新预览。应用继续使用原有写入命令和令牌，不新增写入权限。
前端严格校验文件数量/顺序、路径、格式、摘要及所选详情身份；生产浏览器预览不伪造配置。
共享完整文本的 1 MiB 上限也在前端边界执行。

## P21：回滚 Claude Code 配置

目标：让用户看到 vibemate 写过的 Claude Code 配置操作，预览把某个操作写过的文件恢复成它替换前的内容，
冲突时拒绝覆盖。首个界面只服务 Claude Code；机制放在 `config_apply`，供之后的 Pi/Grok 适配器与 MCP 注入复用。

本模块仍只读写自己记录过的东西：恢复的前提是操作日志里有这个操作，用户手动改回的文件不会变成一条记录。

### 已确认决定（2026-10-14）

- **逐步骤回滚状态（schema v17）。** `config_operation_step` 新增 `restore_state`，取值为 `restored`
  （已写回原内容或已删除新建文件）、`conflict`（文件在写入后被改成别的内容，保持原样）、`unavailable`
  （备份缺失或摘要不符）、`failed`（写回没有完成）、`unknown`（结果无法核对）；空值表示还没尝试。
  没有这一列时，`partial` 操作重试补偿会把已回滚的步骤再恢复一次，`restore_file` 的令牌检查随即返回
  `target_changed`，操作永远停在 `partial`。回滚因此跳过已经是 `restored` 的步骤；每次尝试覆盖同一行，
  不保存尝试历史。
- **写入前是否存在也要记录（同一迁移）。** 一个应用成功的步骤可能没有备份：它新建了文件，或者发现计划
  内容已经在文件里（空操作）。两者在旧日志里长得一样，而把「空操作」当成「新建」会在恢复时删掉用户本
  来就有的配置文件。v17 因此还加了 `previous_existed`：`0` 表示该步骤新建了文件，`1` 表示文件当时已存在，
  空值表示旧版本写的行没记录这件事。空值不猜：预览把它标为 `blocked`，理由码 `restore_history_unknown`。
- **凭据只随文件内容回写。** 恢复不读取 OS 凭据、不改凭据引用：写回的就是备份里的原内容，可能仍含之前
  那家 Provider 的明文密钥。`config_operation` 新增 `owner_ref`（写入该操作的 Provider ID，可为空），
  恢复预览用摘要链判断「恢复后的内容由哪次操作写入」，据此说明密钥归属；判断不出来时明确显示未知。
  全程不读文件内容、不做密钥值比较。
- **日志只增不减。** 本次不删除已结束操作，也不加清理策略；界面按上限读取（默认 10 条，最新在前）。

### 回滚语义与记录

- 恢复**不新增操作行**：它更新原操作与其步骤（操作状态、`restore_state`）。如果把一次恢复记成新操作，
  恢复失败就会留下一个新的未完成操作，P34 的恢复入口会去「补偿」它，等于把用户刚撤掉的配置写回去。
- 原操作的备份保留：它记录的是那次应用替换掉的内容，恢复之后仍可再恢复或用于审计。只有**恢复过程中**
  新产生的副本（写回时被替换掉的当前内容）在写回成功后删除。
- 可恢复 = 至少一个步骤 `state = applied` 且 `restore_state` 不是 `restored`。`applied`、`partial`、
  `unknown` 与写了一半的 `planned` 都可能符合；`failed`（没有步骤写过盘）与 `compensated` 不符合。
- 清理失败不再静默：`BackupStore::discard` 改为返回结果，恢复结果带 `leftovers`（未能删除的副本路径），
  界面显示残留位置并提供继续恢复的入口。
- 竞态与重试：写回时若文件当前摘要已等于备份摘要，说明这一步已经被恢复过（另一次点击或另一次恢复），
  记为 `restored`；只有文件确实是第三种内容时才记 `conflict`。

### 恢复预览（只读）

`config_apply/restore.rs` 的 `plan_restore(storage, operation_id)` 读取操作记录并逐步分类；操作不存在时返回
`None`，由命令层报 `operation_not_found`：

| 步骤情况                                              | 预览动作   | 说明                             |
| ----------------------------------------------------- | ---------- | -------------------------------- |
| 当前摘要 = 记录的应用后摘要，且有可读且摘要相符的备份 | `restore`  | 写回备份内容                     |
| 同上，但该步骤当时新建了文件（没有备份）              | `remove`   | 删除 vibemate 新建的文件         |
| 文件存在但摘要不等于应用后摘要                        | `conflict` | 用户或其它工具改过，拒绝覆盖     |
| 备份缺失/摘要不符，或目标是符号链接、超限、不可读     | `blocked`  | 带稳定原因码与处理提示           |
| 没有备份、旧日志未记录写入前是否存在                  | `blocked`  | 理由码 `restore_history_unknown` |
| 没有备份，且旧日志说明文件当时已存在（空操作）        | `skip`     | 没有需要恢复的内容               |
| 步骤不是 `applied`，或已经是 `restored`               | `skip`     | 不触碰                           |

预览只返回路径、摘要、动作与状态，以及由 `owner_ref` 解析出的密钥归属说明；**不返回备份内容**。
摘要不是秘密，路径是用户自己的文件路径，因此历史列表同样只带这两类信息。

### 恢复应用

`apply_restore(storage, operation_id, reviewed, backups)` 先用与预览相同的代码重新构建计划，再逐项核对
界面回传的令牌（步骤序号 + 预览时的当前摘要），任一不符返回 `plan_stale` 且不写任何文件。通过后按应用顺序的
**倒序**处理可恢复步骤，每步写入 `restore_state`；`conflict`、`blocked`、`skip` 步骤不动。操作最终状态：
全部恢复为 `compensated`，否则 `partial`；任何一步结果无法核对时为 `unknown`。返回值带逐步骤结果、操作状态与
`leftovers`。

`compensate_operation` 保持原语义（自动回滚未完成操作，事务失败后调用），但改为复用同一份逐步骤回滚实现，
因此两条路径的冲突判定与记录方式一致。

### 命令与界面（P21.c / P21.d）

  `apply_claude_code_restore`。三个命令都走 `with_restore_storage`；恢复不读凭据，所以不取凭据锁。

## Grok Build 预览（P22）

Grok 把所有用户设置放在一个 `config.toml` 里，所以本适配器的计划只有一个目标文件。
`config_plan::read_target_bytes` 从原来的 JSON 读取器里拆出「文件身份 + 精确字节」这一步，
JSON 与 TOML 读取器共用它，避免「计划认为未变、写入认为已变」的分歧在第二种格式上重现。

- **保留原文件形态**：解析与合并用 `toml_edit`（已在锁定的依赖图里，不新增 crate 版本），
  它按文档结构改写目标字段，保留用户自己的注释、键顺序与无关表；换成纯值模型会丢掉这些。
  解析失败的文档直接拒绝，不改写、不「修复」。
- **合约检查跟着安装版本**：Grok 启动时把随版本发布的配置参考解包到
  `<root>/docs/user-guide/26-config-reference.md`，并写 `<root>/.metadata_version`。适配器要求
  下载文件名版本、`.metadata_version` 与该参考里的字段行三者一致，任一不符返回
  `agent_version_unverified`；两个文件都按有界普通文件读取，符号链接即拒绝。
- **别名归属**：`[model.<alias>]` 是配置身份。schema v19 `grok_model_binding` 按
  `(config_root, model_alias)` 记录中心 Provider/模型对；没有记录的同名条目属于用户，
  候选别名会跳过它另取一个，而不是接管。归属按配置根隔离，`GROK_HOME` 指向另一套安装
  时不会继承另一套的声明。
- **只写有文档依据的字段**：`model`、`base_url`、`name`、`api_backend`、`api_key` 与
  已声明的 `context_window`，加 `[models].default`。请求参数（`temperature`、
  `top_p`、`max_completion_tokens`）与 `reasoning_efforts` 留给 P24 的逐项核实映射。
  已有 `env_key` 的条目保留该行不改写，但明示 `api_key` 会接管认证来源。
- **会写但不能选中的组合先拒绝**：别名出现在 `[models].disabled_models`，或
  `[models].allowed_models` 非空且既不含别名也不含模型 ID 时，返回 `target_conflict`。
  这比写入后再告诉用户「写了但选不到」诚实。
- **未核实的协议不猜**：`api_backend = "messages"` 时官方只示范把 `x-api-key` 放进
  `extra_headers`，没有说明模型自己的 `api_key` 会被放进哪个请求头，因此
  Anthropic Messages 路由返回 `protocol_unsupported`。
- **覆盖来源只声明存在**：`managed_config.toml` 与 `requirements.toml` 只报告
  「不存在 / 存在 / 不可读」，不读内容——那里可能有另一家的明文密钥。`GROK_CONFIG`
  覆盖层与环境变量、CLI 参数在本批不探测，界面按「未读取的高优先级来源」说明。

### 应用与回滚（P23）

`OperationKind::GrokSettings`（`grok_settings`）复用同一份日志、私有备份与补偿实现；
`config_operation.kind` 只限长度、由 Rust 判定合法值，因此接入第三种操作类型不需要迁移。
应用先重建计划并逐令牌比对（路径、文件摘要、别名、Provider revision、模型摘要），任一变化
返回 `plan_stale` 且不写字节；随后才读 OS 凭据，把预览里唯一的掩码位置换成真实密钥，其余内容与
预览所见一致，由 `toml_edit` 负责引号与控制字符的转义。写入走私有模式（Unix 替换后为 0600），
原内容进私有备份，重读失败或摘要不符报 `outcome_unknown`。

别名归属只在步骤确实写盘（`applied`）之后记录；被拒绝或已回滚的写入不认领别名，因此下一次预览
不会去改一个从未被本适配器写过的条目。记录后即使恢复原文件也保留该行：它描述发生过什么，
并让后续预览沿用同一别名，而不是留下一份孤立条目和一个新名字。恢复按 Agent 隔离，
Claude Code 与 Pi 的入口拒绝 Grok 的操作 id，反之亦然。

界面侧：Grok 卡片的应用按钮与结果卡沿用 P20/P21 的机制，只有文案按 Grok 自己的说法
（`grokOutcomeApplied` 与 `grokRestartRequired`）；`RestoreView` 的命令名改为按 Agent 查表，
新增适配器不再往三个函数里各加一个三元分支。

仍未做：`requirements.toml` / MDM 与 `GROK_CONFIG` 覆盖层的内容检查（只报告存在）、
`[model_providers.<id>]` 共享块的接管、请求参数与推理档位映射（P24），以及本机真实 Grok
会话的应用/恢复验收。
