## [Unreleased]

### Documentation

- Clarified pending configuration-history requirements: independent pre-write snapshots, including restores, full history browsing, direct restoration of any retained version, and confirmed record/backup deletion with retryable cleanup. Added explicit follow-up tasks for verified Agent mappings and UI for reasoning efforts, context windows, output metadata and supported request settings. These are plans, not newly implemented application features.

### Fixed

- Added the typed frontend boundary for complete configuration history. Strict Zod schemas reject unexpected fields, contradictory journal/reconciliation metadata, invalid ordering and mismatched pagination cursors; errors discard raw responses and validation diagnostics. Browser preview does not invoke IPC or invent history. Zod 4.6.7 (stable, MIT) is now an explicit application dependency, with the lockfile updated. Verified with 79 new boundary tests, the full frontend checks (989 tests), Rust formatting/Clippy/tests (514 passed, 1 ignored), and the locked macOS no-bundle build. Existing history screens have not switched to this wrapper; native invocation acceptance and Windows/Linux verification remain pending. The existing large-chunk advisory remains.

- Added a read-only Rust desktop command for complete, root-scoped Claude Code, Pi and Grok Build configuration history. It shares discovery's environment precedence, accepts only a supported Agent identity and pagination fields, and remains usable after an installation or target directory is removed. Responses contain journal metadata, not configuration bytes, private backup paths, backup-availability claims or recovery approval. Existing history and restore screens are unchanged; frontend integration and native invocation acceptance remain pending. Verified with five new boundary tests, Rust formatting, warning-free Clippy and the full suite (514 passed, 1 ignored), frontend checks (910 tests), and the locked macOS no-bundle build. No real Agent configuration was changed; Windows/Linux runtime checks remain pending. The existing frontend large-chunk advisory remains.

- Interrupted configuration writes now offer **Inspect interrupted write** in Claude Code, Pi and Grok Build history instead of an unusable restore action. The bilingual review shows each file's mutation direction, journal stage, observed digest relationship and independent-backup availability. Only a backend-approved, unchanged complete review can be recorded; ambiguous, diverged, unreadable, damaged or superseded observations remain blocked. Recording repairs journal results without changing configuration or credentials, refreshes history and never automatically restores anything. Strict IPC accepts fixed Agent identities and an opaque review digest, not arbitrary paths or frontend-supplied observations. An isolated macOS Tauri run with synthetic configuration verified real IPC, journal repair, repeated-approval refusal and a separately confirmed restore back to the original bytes; browser fixture review covered English/Chinese, keyboard actions, blocked state, long paths and a 480 px content column in light/dark themes. Rust formatting, warning-free Clippy, the full Rust suite (496 passed, 1 ignored), frontend checks (910 UI/boundary tests) and the locked macOS no-bundle build passed; the existing frontend large-chunk advisory remains. Full history browsing, configuration-root isolation, current-version detection, maintainer UI acceptance and native Windows/Linux verification remain pending.

- Added backend inspection and explicit cleanup for private backup copies left without a journal reference after a pre-write log failure. Cleanup checks all legacy-step and per-mutation references under the shared configuration lock and a SQLite write transaction, refuses changed approvals, and never recursively deletes unknown layouts or follows backup-entry symlinks. Failed or interrupted cleanup remains discoverable after restart; already-removed copies can be retried. Configuration files, history records, credential storage and ownership bindings are untouched. This has no IPC/UI entry and does not run automatically; full history management remains pending. Verified with 12 new fault/concurrency tests, Rust formatting, warning-free Clippy and the full suite (491 passed, 1 ignored), frontend checks (864 UI/boundary tests), and the locked macOS no-bundle build. No real Agent configuration was changed; native Windows/Linux checks remain pending. The existing frontend large-chunk advisory remains.

- Configuration restores and automatic compensation now retain independent private snapshots instead of discarding the content they replace. Restoring an absent-file state also backs up the file before deleting it. SQLite schema v20 commits a separate per-file revision before each recorded mutation, linking its source step and apply/restore/compensation batch without adding a reverse-replay job to the legacy recovery queue. Backup or pre-write log failure prevents the mutation; an interrupted result record retains its snapshot and blocks legacy replay until reconciliation is implemented. Unchanged content creates no revision, retained backup files cannot be overwritten by a reused ID, and existing operation history is preserved without inventing missing snapshots. Full history browsing, unresolved-revision reconciliation, direct version restore and deletion remain follow-up work; this is the first backend slice, not completion of H1–H3. Verified with Rust formatting, warning-free Clippy and the full suite (454 passed, 1 ignored), frontend checks (44 files, 864 tests), and the locked macOS no-bundle build. Tests cover exact-byte snapshots, absence versus empty files, restore/compensation batches, pre-write and post-write journal faults, retained snapshots after restart, legacy-replay refusal, backup-ID collisions, failed replacement and the v19-to-v20 migration. No real Agent configuration was changed; native desktop acceptance and Windows/Linux checks remain pending. The frontend build still reports its existing large-chunk advisory.

- Pi preview no longer refuses a compatible installation just because it was updated from 1.2.0 to 1.3.0. Stable Pi 1.x releases from 1.2 use bounded checks of the selected package's published models/settings schemas, including required native field types and compatibility options; the managed launcher follows its active release instead of a fixed release directory. Pi provider keys now use readable saved configuration names, such as `vibemate-OpenRouter`, with a short suffix only on a collision. Recorded UUID entries migrate through the reviewed backup/write flow, retaining all models, scoped-model patterns and per-model reasoning levels. Schema v18 records current and historical alias ownership so renames, duplicate labels and restores cannot silently adopt another account's entry.

### Changed

- Configuration history on the Claude Code, Pi and Grok Build detail pages now reads the root-scoped paginated journal instead of the latest-ten, Agent-only listing. Apply attempts, manual restores and automatic compensation batches appear as separate entries; **Load more history** appends older entries by cursor without shifting rows already read, and a failed page keeps the existing entries with a retry. Each row shows the entry kind, the operation result or the batch's least certain per-file result, time, affected files, per-file state, and the recorded Provider name (or its retained reference after Provider deletion). Interrupted writes keep the existing inspect-and-record action and do not offer a legacy restore. Apply rows offer the read-only restore preview, which reports when the current files have nothing left to undo; the page still reads no target or backup bytes and makes no backup-availability or current-version claim. The paginated response adds only `requiresResolution`, computed by the same journal query that guards recovery, and `ownerLabel` from the saved Provider row. Verified with the full frontend checks (47 files, 996 tests), Rust formatting, warning-free Clippy and the full suite (515 passed, 1 ignored), and the locked macOS no-bundle build. Native desktop acceptance, backup-availability display and current-version pinning remain pending; Windows/Linux behavior still needs its release-time check. The existing frontend large-chunk advisory remains.

### Added

- Backend-only configuration history query combines original apply attempts (including legacy and failed records) with separate restore/compensation batches. Exact Agent/root file scopes exclude other roots and mixed-root operations; bounded seek cursors browse past ten or fifty entries without splitting multi-file batches. Each page uses one SQLite read snapshot and retains explicit reconciliation audits, but never opens target/backup files or exposes copy paths or content. A recorded copy reference is not reported as backup availability, and no current-version or restore eligibility is inferred. The existing IPC/UI remains on the latest-ten, Agent-only listing; this query adds no restoration, deletion or automatic action. Thirteen new real-SQLite tests cover pagination, isolation, grouping, restart, concurrent updates and malformed metadata. Rust formatting/Clippy, the full Rust suite (509 passed, 1 ignored), frontend checks (910 UI/boundary tests) and the locked macOS no-bundle build passed. Windows/Linux native verification remains pending; the existing frontend large-chunk advisory remains.
- Grok Build can preview a saved Provider/model from its Agent detail page. **Model configuration** lists saved provider configurations and their added models, then asks Rust for the changes to `~/.grok/config.toml`: one `[model.<alias>]` entry (`model`, `base_url`, `name`, `api_backend`, a masked `api_key`, and `context_window` only when the saved model states one) plus `[models].default`. The card names the file and its SHA-256 change token, whether that alias already exists, and the higher-precedence files it located but never read (`managed_config.toml`, `requirements.toml`). It states that a new Grok session is needed, that the key is read from OS credential storage only when a change is applied and then lands as plain text, and — when the entry already points at an environment variable — that the planned key takes over that entry while its existing line is left alone. Refusals are explicit and translated: an alias the maintainer wrote and vibemate never recorded, an alias that is disabled or outside an allowlist, a key holding another shape, a file that does not parse, a Grok version whose own launch-extracted configuration reference does not match the verified field set, a protocol switch on an address the vendor does not document, and an Anthropic Messages route whose credential header is not yet verified. SQLite schema v19 records alias ownership per configuration root, so a `GROK_HOME` installation cannot inherit another root's claims.

- **Applying a Grok Build preview** now writes it. **Apply these settings** rebuilds the whole plan and compares every token the card showed — settings path, file digest, chosen alias, Provider revision and model digest — and refuses with `plan_stale` when any of them moved, so an edit made while the card was on screen is never overwritten. The OS key is read only after those checks and replaces the one masked position the preview showed; `toml_edit` quotes and escapes it, so a key containing a quote or backslash stays one literal value. The result states which of the five outcomes happened, names the file and reason for a refused step, points at the private copy of the previous content, and asks for a new Grok session only when the file now holds the planned key. Unowned content survives byte for byte: the maintainer's own model entries, their keys, `reasoning_efforts` rows, MCP servers and `[ui]` settings are not this plan's fields, and a restored write puts the original file back exactly as it was. Ownership of the alias is recorded only for a step that really reached the disk, and the history stays per Agent: a Grok row cannot be undone from the Claude Code or Pi page and the other way round.
- The configuration writer no longer parses the target file. It compares exact bytes, which is what a plan and its write must agree on, while the document format belongs to the adapter that planned the change; requiring JSON would have turned the first adapter's format into a condition every later adapter has to satisfy. The shared history and restore commands are reached through one per-Agent command table instead of three duplicated branches.

The Windows/Linux checks remain open.

- Pi installations with a compatible published 1.x configuration format can preview and apply a saved provider/model from its Agent detail page. The preview shows changes to `models.json` and `settings.json`, masks both old and new API keys, and binds both files, the read-only `auth.json` precedence check, the provider revision and model digest. Application reads the key from OS credential storage, escapes Pi command/environment syntax, preserves unrelated providers/models/settings, keeps private original-file backups and compensates earlier writes if a later file fails. The preview names every file and what would happen to it — write the stored copy back, remove a file the write created, leave it alone because it changed afterwards, or report that the stored copy is unusable — and names the Provider whose key the restored content carries when the log can prove it, including when that Provider no longer exists. Confirming sends the digests the preview showed, so a file that changed again is refused with `plan_stale` instead of being overwritten, and the restored file gets back whatever it held before the write — including a plain text API key if it contained one; OS credential storage is not touched. - A partly rolled back configuration write can now be finished. The operation log records what a rollback did to each applied step (schema v17: `restore_state`), so a second attempt skips the steps it already restored instead of seeing its own earlier work as a user edit and getting stuck; a file that already holds the previous content counts as restored, and only a file changed to something else stays a conflict. The log also records whether a step found its file already on disk (`previous_existed`), because a write that found the planned content in place keeps no copy just like one that created the file — without that fact a restore would have deleted a settings file that was already there. A row written before this build is reported as blocked rather than guessed at.

- UI scenarios no longer run once per locale when the locale only decides which strings the test queries. Those cases tested the same code path twice; the translation-resource check already enforces key, placeholder and plural parity, so one run in English is enough. Removed the tests that asserted them: provider and Agent icon files and positions, the Agent status dot's `data-state`, the window drag-region containment check, the primary-button class filter, and the MCP Save-in-header position. - Reworked the frontend documentation to keep rules, contracts and security boundaries while dropping detail the code already states: implementation micro-values, per-component style inventories, hardcoded per-run test counts and completed-task process narration. Removed the retired HTML layout preview, which still advertised an outdated Settings UI, and trimmed stale verification tallies and tool versions from the completed task plans.
