# vibemate 第一阶段开发计划

日期：2026-10-09。进度与验证记录以 [todo.md](todo.md) 为准；下一步按该清单的依赖顺序实施。

## 目标与范围

做一个集中管理 Provider、Model、Skill 和 MCP Server 的桌面工具，将配置
按各 Agent 的实际能力注入。第一阶段的 Provider 是 Command Code、
DeepSeek、OpenRouter；Agent 是 Pi、Grok Build。目标平台是 macOS、Windows、Linux；第一阶段界面支持简体中文与英文。

使用当前稳定版 Rust、最新稳定 Edition、稳定版 Tauri、React 和 TypeScript。
遵守根目录 `AGENTS.md`、`src/AGENTS.md`，代码注释和公开 API 文档使用英文。
计划说明使用中文，便于维护者审阅。许可证为 MIT。

本文件记录设计、依赖和风险。**唯一执行清单是 [todo.md](todo.md)**。
依照仓库规则，两个文件都直接放在 `docs/plans/`；不建立另一套 `tasks/` 清单。

## 关键设计

### 1. Provider 与 Agent 分开适配

Provider 适配器描述端点、认证、协议、模型发现和特有参数；Agent 适配器描述
配置格式、优先级、模型/Skill/MCP 支持、配置位置及生效方式。分别维护能力声明，
不能默认所有服务商兼容同一协议，或所有 Agent 都支持 MCP。

内置模板提供易用入口，同时保留自定义 URL、认证请求头和经过验证的扩展字段。
一个 Provider 可有多个账户配置，以稳定 ID 标识，不以显示名称关联。
Model 配置属于 Provider 实例，用实际模型 ID 标识；别名只用于显示。

先接通 DeepSeek 与 Pi 的一条真实配置路径；若 P01/P02 发现协议不兼容，优先使用
已确认兼容的 Provider/Agent 组合，并记录改序原因。不能为了坚持顺序偷偷加代理。
其余两家服务商与 Grok Build 复用适配边界，而不复用未经验证的协议假设。

### 首页关系与启停约定

维护者已提供首页草图：上方 Provider，下方 Agent，两侧共享 Skills/MCP，中央汇合
并应用配置。绿色表达启用状态；选中状态单独表达。维护者要求在继续功能前固定桌面壳，
以 [desktop-shell-design.md](desktop-shell-design.md) 为设计基准：固定侧栏与关系首页，
侧栏可收起为 88 px 图标栏，右侧不设独立标题栏；macOS 原生红黄绿位置不随折叠变化。
语言与外观位于 Settings →「常规」分组列表（下拉选择）；顶栏页签为「常规 / 关于」（关于页展示真实版本、许可证与仓库地址，见 I02.d）。
修订预览为设计基准；生产壳、macOS Overlay 标题栏与 Win/Linux 无边框窗控已实现（见 `docs/frontend.md`）。
**I02 已完成**：Settings「关于」通过 `get_app_info` 显示真实版本，预览与失败状态明确。侧栏固定 200/88 px（I02.e 拖动调宽已取消）。细节见 todo.md I02.d。
共享资源开关与逐 Agent 注入开关分开，中央内容关闭后保留，停用单个目标不影响其他
目标。操作状态区分请求、已应用、被覆盖、待重载、失败与未验证的当前会话状态。
每种开关映射到各 Agent 核实的原生操作，不预设它们都提供同名 enabled 字段。
详细边界见 `docs/architecture.md` 和 `docs/integrations/pi.md`。

### 2. 能力信息与请求参数分开

上下文窗口、输入模态、工具调用、推理支持属于能力信息；温度、输出上限、推理努力
或推理预算属于请求参数。保留信息来源、获取时间和手动覆盖状态。

修改能力标签不会让模型获得新能力。参数必须按 Provider 协议和 Agent 字段分别校验；
没有明确等价关系时，不把推理 effort 自动转换为数值预算。保存支持的原始扩展字段，
拒绝注入未知或不支持的设置，并说明原因。

### 3. Rust 负责配置与系统操作

一个 Rust crate 起步，按功能逐步增加模块；Tauri command 只做输入输出边界。
维护者提出未来 GitHub/Vercel、更多 MCP 与模型服务商扩展后，新增
[后端职责拆分计划](backend-modularity.md)，任务状态见 `todo.md` 的 BR 系列。
近期建议先拆内联测试、命令入口和 Provider/MCP 职责，保留 IPC、schema、凭据引用
与并发语义；本轮完成规划，尚未实施代码迁移。云服务账号/授权独立于模型服务商
与 MCP 定义；后续业务实际接入时再抽取必要的通用 HTTP transport。
维护者补充的配置备份到 GitHub、MCP/Skill 来源安装和给 Agent 的 API 转发，分别规划
`backup`、`sources/installation` 和 `gateway/protocols`；这些是后续扩展意图，尚未实现，
不因本次模块规划自动扩大现有第一阶段验收范围。Agent 直接安装也作为未来需求记录：
安装/升级/卸载属于 installation；agents 继续负责发现、版本能力和配置管理。
React 使用 `src/features/<feature>/`，通过 `src/lib/desktop/` 下的类型化封装调用 Rust。
IPC 返回值要做运行时校验，复杂数据出现时再引入适合的 schema 工具。

首次 Provider 保存时引入 SQLite，包含稳定 ID、schema version、迁移和有界分页查询。
密钥交给 OS 凭据库，数据库仅保存引用；用假凭据库和临时数据库做自动测试。
具体 Rust 库在对应任务开始时核对当前稳定版、维护状态和 MIT 兼容性。
不预设 SQLx、ORM、状态库、路由库或 UI 框架；选择应与实际需求相称。

数据库与凭据库不共享事务。密钥写入、元数据保存和删除必须设计补偿步骤，避免
失败后残留不可恢复的配置或泄漏孤立凭据。OS 凭据库不可用时显示明确错误，不能
回退为明文 SQLite。UI 只临时持有用户输入的密钥，提交/取消后清理。

第一个网络请求是 P12 的「获取模型」，只在用户点击时发送。HTTP 客户端为
`reqwest 0.13.5`（关闭默认特性，使用 `rustls-no-provider` 与 `system-proxy`），加密实现为
rustls 的 ring，不引入 aws-lc 或 native-tls；证书用操作系统信任库校验。应用读取系统代理：
先读 `ALL_PROXY`/`HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY`（含小写），未设置时读 macOS/Windows
系统设置，Linux 只读环境变量。测试通过可注入的客户端设置调用 `.no_proxy()`，模拟服务器不受
代理环境变量影响。请求在 Tauri 已有的 tokio 运行时上异步执行，用户取消时立即中断。

### 4. 注入必须可预览、可恢复

流程：发现安装 → 解析优先级 → 读取现状 → 校验支持范围 → 生成脱敏差异 →
重新检查文件状态 → 私有备份 → 同目录临时写入与原子替换 → 验证 → 可回滚。

保留不由 vibemate 管理的字段。计划记录原文件摘要；应用时原文件变化就拒绝旧计划，
要求重新预览。多文件变更不声称有文件系统事务：记录操作步骤，失败时补偿，并在
下次启动发现未完成操作。跨卷、符号链接、权限、Windows 替换行为都需单独验证。

**密钥注入是前置设计问题。** OS 凭据引用本身不能被外部 Agent 自动读取。如果
Agent 支持环境变量引用，需要验证它实际从何处获得变量；桌面进程的环境变量不会
自动改变已有终端。若 Agent 原生配置要求明文密钥，用户的应用动作应明确展示这一点，
只写入该 Agent 的私有配置，约束权限并对差异、备份展示和日志脱敏。含密钥备份保存在
私有目录，不作为普通导出。不能用“数据库只保存引用”掩盖目标配置中的明文。

默认目标是：用户从原有方式启动 Agent 时，原生配置生效。若某 Agent 必须经过
vibemate 启动器或本地代理，先向维护者说明限制并决定范围，不静默改变使用方式。

### 5. Skill 的来源与部署分开

中央目录保存 Skill 的身份、来源、固定 revision、内容摘要、安装方式和本地修改状态。
目标 Agent 的部署记录另存，使用 symlink；权限或平台不支持时提供明确的 copy-sync。
只管理自己的部署条目，不能删除 Agent 目录中已有的同名用户内容。

支持 GitHub 来源、已安装的本地 Skill，以及 Vercel/npx 安装产生的 Skill。
不能只根据目录名猜出来源或更新命令；缺少来源时显示不可自动更新，并允许补充。
Git 源在隔离目录获取固定 revision；npx 源需要核实实际安装器与参数，先展示准确命令，
隔离安装并检查退出状态，不能执行 Skill 文档中的任意命令。

更新先生成内容差异，再应用；本地修改要能保留或选择处理方式。中央目录与多个 Agent
目标不是一个原子事务，需要部署日志、错误状态和可恢复的补偿步骤。

### 6. MCP 定义与执行分开

中央维护结构化 MCP 定义，包括 stdio 命令/参数/环境变量和已确认支持的 HTTP 传输。
认证值使用凭据引用；不把敏感 env/header 放入普通导出。保存和预览不启动服务器。

只按各 Agent 已核实的 MCP 格式映射。无原生支持时明确显示不支持，不能通过写一个
无效 JSON 文件假装完成。桥接器或 Agent 扩展属于额外决策，先记录方案再由维护者
决定；如第一阶段必须具备该能力，未解决前不能把第一阶段标为完整交付。

### 7. 中英文是第一阶段基础

在业务页面开始前完成 P07–P09。采用当前稳定的 i18n 方案，建议 i18next/react-i18next；
实施时核对维护状态、React/Vite 兼容性与类型支持，不自建复杂翻译引擎。
支持 `zh-CN` / `en`，默认跟随系统，允许手动选择，未知语言回退英文。
中文变体统一映射到简体中文，不在这一阶段承诺繁体中文。偏好通过 Rust 保存于
app-data；启动时先确定偏好再显示业务界面，切换无需重启且不重置表单。

所有标题、表单、校验提示、状态、确认对话框和可访问名称使用稳定翻译键。
日期、数字、复数和插值按语言处理；完整句子作为翻译单元，不拼接片段。
Provider/Model ID、品牌、URL、文件路径和用户内容保持原值，不影响注入配置。
Rust 使用稳定错误 code 与安全参数，前端决定语言；不翻译配置字段或处理脱敏前的原始错误。

资源 key、空值、插值参数与必要复数形式要做自动校验，并接入 `check:frontend`。
类型约束与校验防止遗漏；找不到翻译时使用明确的英文后备，不把 key 暴露给用户。
每个业务任务同时更新中英文；资源、测试和接线都计入文件范围，需要时先拆子任务。
新增窗口/对话框同时考虑语言同步，HTML lang、动态窗口标题与屏幕阅读器状态保持一致。

## 执行与完成标准

1. 切换工作区后先读本文件、`todo.md`、两份 AGENTS 文件和实际代码；不要重建骨架。
   单人顺序执行；不使用子代理，除非维护者以后明确批准。
2. 业务接入从 P01 起按清单依赖推进。资料不全时列出准确缺项，不伪造实现或扩大范围。
3. 每项任务列出的路径是建议的主要文件。开始前按实际结构确定文件与测试位置；
   **总共超过约五个文件或超过一个专注会话，就先在清单中拆成子任务**，包含注册、
   锁文件、迁移与测试。不得用“只是接线”掩盖一个过大的任务。
4. 先用针对性测试覆盖风险行为，再完成实现与必要检查。界面测试验证用户行为，
   不只验证静态标签。Rust 模块内测试可先共置；迁移/文件操作使用独立临时目录。
5. `todo.md` 的验收条件全部满足、实际跑过 Verification 后才能勾选。长篇执行记录
   不写在清单里（以提交与 CI 为准）；未解决的验证缺口或平台限制在对应任务下简短注明。
6. 更新相关学习文档和英文 CHANGELOG；每个完成的任务尽量形成独立本地提交。
   进入新阶段前解决该阶段的协议/范围疑问，不重复询问已经明确授权的普通实施步骤。
7. 任务状态与验证记录以 `todo.md` 为准。

### 验证命令约定

当前已有：

```sh
pnpm run check:frontend
cargo fmt --manifest-path src-tauri/Cargo.toml -- --check
cargo clippy --manifest-path src-tauri/Cargo.toml --locked --all-targets -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --locked
pnpm run tauri build --no-bundle -- --locked
```

UI 验证使用 `pnpm run test:ui`（已纳入 `check:frontend`）或
`pnpm run test:ui <测试文件>`；Rust 使用
`cargo test --manifest-path src-tauri/Cargo.toml --locked <测试过滤词>`。
清单中的文件名/过滤词是预期名称，实施时与实际测试同步，防止过滤词匹配零条测试。
纯文档任务只做事实、链接与格式检查，不为文档变更重跑所有原生构建。

前端变更运行 `check:frontend`；Rust 变更运行相关测试、fmt、Clippy；涉及 IPC 或
原生写入时检查实际 Tauri 运行。阶段检查点和发布前运行完整检查，正常任务避免
没有依据地重复全量构建。可见界面用 ego-browser 检查，包含 720×560、长内容、
键盘与错误状态；浏览器预览不证明原生操作正确。

## 风险与处理

| 风险                                    | 影响                 | 处理                                          |

| 产品名称、协议或版本不明确              | 错误接入与返工       | P01–P03 记录官网、版本、字段示例和证据日期    |

## 待核实事项

- Command Code 与 Grok Build 的准确官网/文档/发行来源、账户/API 类型。Command Code 的 API 访问证据目前只覆盖其 GOAT 套餐；
  Pro 与 Provider 套餐的 API 访问、模型权限与路由尚未核实，不能套用 GOAT 套餐的结论。
- Pi 与 Grok Build 的安装方式、本机版本、跨平台可用性、原生协议、Skill/MCP 支持。
- MCP 无原生支持时，是否需要第一阶段增加桥接器；决定前对应交付保持未完成。
- npx/Vercel Skill 的具体安装器、源仓库记录方式、更新命令与覆盖行为。
- i18n 范围已确认：第一阶段简体中文与英文；默认跟随系统，未知语言回退英文。
- 真实验收时哪些账户可提供测试凭据、允许的测试请求与安装环境。
- GitHub 仓库、发布签名和公证凭据在需要时配置；本计划不创建远端或发布标签。

## 第一阶段最终验收

- 三家 Provider 可按其真实协议配置；Model 信息与参数能保存、校验并映射。
- Pi、Grok Build 的兼容配置可预览、应用、回滚，原有启动方式按支持矩阵生效。
- Skill 可维护来源、部署和更新，保留已有内容与本地修改；同步失败可恢复。
- MCP 可集中维护并注入已支持的 Agent；任何剩余支持缺口须有维护者明确决定，
  不能用“不支持”的提示代替原本要求的能力并宣称阶段全部完成。
- 中英文覆盖全部用户界面与可访问名称；切换和持久化通过，翻译一致性检查接入 CI。
- 三平台检查、真实接入证据、严格前端检查、英文注释、MIT 和 CHANGELOG 发布规则通过。
